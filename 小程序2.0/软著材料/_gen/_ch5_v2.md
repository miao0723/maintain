## 5.1 功能模块总览

本系统由微信小程序客户端、Node.js（Express）服务端、PHP（ThinkPHP）Web 管理后台与 Python（FastAPI + LangGraph）智能客服 Agent 四部分协同构成，功能模块覆盖"客户自助服务—后台运营管理—智能辅助决策"全链路，并与企业资产管理（设备台账、工单、进销存）深度融合。各功能模块总览如下：

| 分组 | 主要功能模块 |
| --- | --- |
| 客户端（小程序 + Node 后端） | 用户登录与认证、个人中心、地址与单位管理、设备管理、AI 故障自检、智能客服、维修下单、回收流程与估价、报价与确认、维修进度反馈、维修记录、微信支付、订单评价、售后管理、通知与消息推送 |
| 管理端（Node admin / super-admin） | 管理员登录与工作台、订单/工单管理、用户管理、设备类型管理、价格管理、配件与库存管理、数据统计与看板、配送分配、人工客服后台、系统设置、权限控制 |
| Web 管理后台（PHP CMMS） | 登录与 RBAC 权限、设备台账管理、工单全生命周期管理、维修人员与排班管理、巡检管理、保养计划管理、维修业务管理、支付与发票管理、进销存管理、统计报表、知识库与向量检索、营销引流、通知中心、mini-admin 小程序后台 |
| 智能客服 Agent（Python） | 智能体工作流（LangGraph）、RAG 知识库检索 |

在整体流程上，客户端负责用户自助办理（登录、下单、支付、评价、售后），管理端负责订单与运营处理（接单、报价、进度、配送、客服），Web 管理后台专注企业侧设备资产与维修保障的台账化、流程化管理，智能客服 Agent 则在客户端与管理端之间提供统一的智能问答与业务引导能力。四者通过统一的接口网关与共享数据库（repair 库）和独立数据库（cmms_db 库）联动，形成"前端体验到后台管理的数字化闭环"。

## 5.2 角色—功能权限映射

系统采用 RBAC（基于角色的访问控制）权限模型，将 user（客户）、internal（内部人员）、admin（维修管理员）、super_admin（超级管理员）四类角色与功能模块做矩阵映射。服务端在接口层通过 auth 与 adminAuth 中间件强制校验角色，前端则按角色动态渲染菜单与入口；客户端与管理端复用同一套接口，仅通过令牌所携带的角色区分访问范围，形成"接口强制 + 前端引导"的双层权限防线。Web 管理后台（PHP）另设独立账号体系与独立 JWT，通过 roles / permissions / role_permissions 三表实现细粒度权限分配，mini-admin 再以独立令牌与主后台隔离。角色—权限的主次职责如下表所示：

| 角色 | 主端点 | 核心权限范围 |
| --- | --- | --- |
| user（客户） | 小程序客户端 | 注册登录、设备管理、AI 诊断、智能客服、维修/回收下单、报价确认、支付、进度查看、评价、售后申请 |
| internal（内部人员） | 小程序客户端 | 客户全部能力 + 内部免付款下单 |
| admin（维修管理员） | 小程序管理端 | 订单/工单处理、用户管理、设备/价格/配件维护、进度审批、配送分配、人工客服、统计看板 |
| super_admin（超级管理员） | 管理端 + 后台 | admin 全部能力 + 系统参数配置、后台所有管理功能 |

## 5.3 客户端功能模块

客户端功能模块以微信小程序为载体，面向客户与内部人员，提供从登录认证、设备管理、故障诊断、智能咨询到维修/回收下单、报价确认、支付、进度跟踪、评价与售后的完整自助服务闭环。该端依托 Node.js（Express）后端统一的 RESTful 接口与 WebSocket 实时通道，实现了"用户自助 + 平台响应"的高效服务模式。

### 5.3.1 用户登录与认证

#### 5.3.1.1 微信授权登录

**功能说明**：作为用户进入系统的第一入口，通过微信生态的免密授权完成身份识别，省去传统注册流程，降低使用门槛。

**实现流程**：① 小程序冷启动或未登录态下，前端调用 `wx.login` 获取临时登录凭证 code；② 将 code 随 `POST /api/user/login`请求提交至后端；③ 后端调用微信开放平台 `jscode2session` 接口，以 code 换取该用户在当前小程序内的唯一身份标识 openid（以及用于消息推送的 unionid、session_key）。

**技术要点**：code 为一次性凭证，5 分钟有效期且单次使用即失效；后端对小程序 appid/secret 严格保密，session_key 仅本地使用不落库明文。

**数据与接口**：涉及 `POST /api/user/login`、`wx.login`、`jscode2session`；返回 openid/session_key 供后续用户识别与消息订阅使用。

#### 5.3.1.2 用户身份换取

**功能说明**：将微信侧的 openid 映射为系统内部业务账号，确立系统内唯一用户标识，是后续下单、订单、设备等一切业务数据归属的基础。

**实现流程**：① 后端以 openid 为主键查询 users 表；② 命中记录则复用既有账号并更新最近登录时间；③ 未命中则进入自动注册环节。整体实现"一次授权、静默登录"，用户全程无感知即可完成"识别—建档—登录"。

**技术要点**：使用数据库唯一索引保证 openid 不重复；对 openid 做脱敏处理，不直接作为链路追踪字段对外暴露。

**数据与接口**：涉及 users 表（openid / unionid / nickname / avatar / phone / role）；该环节在登录接口内部原子完成。

#### 5.3.1.3 新用户自动注册与老用户绑定

**功能说明**：解决"首次使用者建档"与"再次使用者身份复用"两个场景，做到自动注册与既有账号平滑绑定。

**实现流程**：① 新 openid 触发 INSERT，默认初始化角色为 user（客户）、绑定空资料并记录注册时间；② 老 openid 走 UPDATE 逻辑刷新登录时间、回填上次资料同步状态；③ 注册与绑定完成后统一进入令牌签发环节，保证新老用户走同一条后续链路。

**技术要点**：注册与登录在同一数据库事务内完成，避免并发重复建档；用户协议与隐私政策授权状态随首次登录联动落库。

**数据与接口**：涉及 users 表 INSERT/UPDATE；对外仍对前端表现为一次统一的登录请求。

#### 5.3.1.4 头像获取

**功能说明**：支持用户从微信头像库选择头像，既满足《微信小程序用户头像获取规范》，又简化用户操作。

**实现流程**：① 资料补全或编辑页放置 `<button open-type="chooseAvatar">`；② 用户点击触发微信官方头像选择器；③ 选择完成后前端获得临时头像文件路径，并保留供下一步上传。

**技术要点**：遵循微信"头像昵称填写能力"规范，不再使用曾经的 getAvatarUrl 旧接口；临时文件仅作用于当前会话，需在上传接口中落地持久化。

**数据与接口**：涉及 `chooseAvatar` 能力；临时头像文件路径经上传链路写入 users.avatar。

#### 5.3.1.5 昵称获取

**功能说明**：一键回填微信昵称，减少手动输入成本，提升资料完善率。

**实现流程**：① 使用 `<input type="nickname">` 微信官方昵称输入组件；② 用户点击时弹出一键回填微信昵称；③ 用户可保留默认值或修改后提交，前后端对长度与非法字符做校验。

**技术要点**：昵称字段支持 emoji 与多语言，写入前统一做 UTF-8 长度与敏感词过滤，避免脏数据。

**数据与接口**：涉及 users.nickname；提交走资料更新接口 `PUT /api/user/info` 或注册补全接口。

#### 5.3.1.6 头像压缩上传保存

**功能说明**：将头像临时文件安全落盘并以统一 URL 对外访问，同时通过压缩控制存储体积与加载性能。

**实现流程**：① 前端以 multipart/form-data 上传头像文件；② 后端 multer 接收并限制文件类型与大小；③ 经 sharp 对图片做尺寸缩放与质量压缩（限制最大边、输出 JPEG/WebP）；④ 写入 `uploads/avatars` 目录并以日期+随机串命名；⑤ 返回可访问 URL 并写回 users.avatar 字段。

**技术要点**：为防止恶意上传，对图片做真实 MIME 校验；文件名使用随机化避免路径遍历；静态资源通过专用路由/nginx 提供访问。

**数据与接口**：涉及文件上传接口与 users.avatar；依赖 multer、sharp 中间件。

#### 5.3.1.7 JWT 令牌签发

**功能说明**：登录成功后为用户颁发身份凭证，作为本次会话内所有受保护接口的鉴权依据。

**实现流程**：① 后端使用 jsonwebtoken 签发 JWT；② payload 中携带 userId、openid 与 role 等关键身份信息；③ 设置令牌有效期与签名密钥；④ 令牌随登录响应返回前端，由前端存储于 Storage 用于后续请求。

**技术要点**：签名使用密钥加盐保证不可伪造；payload 不存放明文敏感信息；有效期时长兼顾安全与体验。

**数据与接口**：涉及 auth 服务；前端在每个请求头 `Authorization: Bearer <token>` 携带。

#### 5.3.1.8 JWT 令牌验证

**功能说明**：在服务端对每一次受保护请求统一校验令牌真伪与有效期，是接口安全的第一道闸门。

**实现流程**：① auth.js 中间件从请求头提取 `Authorization: Bearer <token>`；② 验证签名完整性并校验过期时间；③ 解析出用户身份后注入 req.user；④ 令牌缺失、伪造或过期时返回 401，前端拦截并自动跳转登录页。

**技术要点**：中间件挂载于受保护路由统一前置；对不同角色接口再叠加 adminAuth 等角色校验中间件，构成"认证 + 授权"两级防线。

**数据与接口**：涉及 auth.js / adminAuth.js 中间件链；异常响应统一为 401/403 语义。

#### 5.3.1.9 角色分流与登录态管理

**功能说明**：登录成功后依据角色将用户引导至对应主界面，并统一维护全局登录态，保证多页面间的身份一致性。

**实现流程**：① 服务端（或本地）按 role 分流：user/internal 进入客户端首页，admin/super_admin 进入管理后台首页；② 小程序 app.js 提供 checkLoginStatus、logout 等方法维护全局登录态与用户信息缓存；③ api.js 统一拦截 401 响应，清理失效令牌并回跳登录。

**技术要点**：登录态采用"本地缓存 + 接口即时校验"双保险；角色变更（如被提升为管理员）后在下次登录时重新分流。

**数据与接口**：涉及 app.js / api.js 全局模块；相关接口 `GET /api/user/info`、`POST /api/user/logout`。

### 5.3.2 个人中心与资料管理

#### 5.3.2.1 个人资料展示

**功能说明**：聚合展示用户基础资料与角色身份，使用户直观了解自身账号信息。

**实现流程**：① 进入"我的"页面触发 `GET /api/user/info`；② 返回头像、昵称、手机号、角色等并渲染到卡片区域；③ 支持下拉刷新以同步最新资料。

**技术要点**：角色以中英文标识映射展示；手机号做中间四位掩码处理，保护隐私。

**数据与接口**：涉及 `GET /api/user/info`；数据源 users 表。

#### 5.3.2.2 个人资料编辑

**功能说明**：允许用户更新昵称、头像、手机号等资料，实现资料的自主维护。

**实现流程**：① profile-edit 页面预填当前资料；② 用户修改后提交 `PUT /api/user/info`；③ 服务端校验并持久化到 users 表；④ 编辑结果实时回显到个人中心缓存。

**技术要点**：手机号变更建议走短信验证（如启用），表单做前端必填与格式校验；头像变更复用上传链路。

**数据与接口**：涉及 `PUT /api/user/info`；更新 users 表。

#### 5.3.2.3 头像上传

**功能说明**：支持随时更换头像，保持账号形象的个性化。

**实现流程**：① 复用 5.3.1.6 的 multer + sharp 上传管线；② 上传成功后更新服务器头像地址；③ 同步覆盖本地缓存头像，实现即时生效。

**技术要点**：与首次设置头像共用同一套上传服务，保证行为一致与可复用。

**数据与接口**：涉及头像上传接口与 users.avatar。

#### 5.3.2.4 账号注销与用户协议

**功能说明**：保障用户数据自主权与知情权，提供账号注销通道与合规协议展示。

**实现流程**：① "设置"提供账号注销入口，二次确认后调用 `DELETE /api/user/delete-account`；② 服务端校验用户未处于未结订单等限制条件后执行注销（逻辑删除）；③ 同时提供用户协议与隐私政策查看入口，以 webview 或富文本展示版本化内容。

**技术要点**：注销为不可逆操作，需二次弹窗强确认；涉及未完成业务数据时给出拦截提示，保障交易安全。

**数据与接口**：涉及 `DELETE /api/user/delete-account`；协议内容 static 资源。

### 5.3.3 地址与单位管理

#### 5.3.3.1 收货地址增删改查

**功能说明**：为上门取件/送修等场景提供发件地址的集中管理，避免每次下单重复填写。

**实现流程**：① address / address-edit 页面提供地址列表、新增、编辑、删除；② 数据经 addressRoutes 的 CRUD 接口持久化到 user_addresses 表；③ 字段含联系人、联系电话、省市区、详细地址及坐标。

**技术要点**：删除采用软删除或在无关联订单时物理删除，防止破坏历史订单关联；地址做默认去重。

**数据与接口**：涉及 user_addresses 表及 address CRUD 接口（`GET/POST/PUT/DELETE /api/addresses`）。

#### 5.3.3.2 默认地址设置

**功能说明**：将常用地址置为默认，下单时自动带入，减少重复选择。

**实现流程**：① 用户将某一地址标记为默认；② 调用 `POST /api/addresses/:id/default`；③ 服务端将同用户其他地址默认态置空，仅保留当前一条默认。

**技术要点**：默认地址唯一性由服务端保证；下单表单优先读取默认地址预填。

**数据与接口**：涉及 `POST /api/addresses/:id/default`；user_addresses.is_default。

#### 5.3.3.3 企业单位增删改查

**功能说明**：面向企业/机构批量送修场景，管理常用单位（收货单位）信息。

**实现流程**：① units / unit-edit 页面维护单位的新增、编辑、删除与默认设置；② 数据写入 user_units 表，含单位名称、联系人、联系方式、地址；③ 服务方式选择"单位"时直接带入。

**技术要点**：单位与企业客户身份关联，支持单位级地址复用。

**数据与接口**：涉及 user_units 表及单位 CRUD 接口。

#### 5.3.3.4 默认单位设置

**功能说明**：标记默认单位，便于企业客户一键选择，提升填写效率。

**实现流程**：① 用户可设置唯一默认单位；② 下单选择"单位"服务方式时自动预填默认单位；③ 与默认地址逻辑一致，保证唯一性。

**技术要点**：与默认地址分表管理、互不干扰，二者均可作为下单收货主体。

**数据与接口**：涉及 user_units.is_default。

#### 5.3.3.5 地图选点与定位

**功能说明**：通过地图可视化选点，精准获取地址坐标，提升上门取/送件地址准确度。

**实现流程**：① map-picker 页面集成高德地图；② 支持关键词搜索、当前位置定位、拖拽选点；③ 通过地理编码（geocode）与逆地理编码（regeocode）在坐标与结构地址间互转；④ 选中后自动回填省市区与详细地址及经纬度。

**技术要点**：地图坐标遵循国内测绘合规（GCJ-02 坐标系）；接口封装于 locationRoutes，统一签发地图服务 key 管理权限。

**数据与接口**：涉及 locationRoutes 及高德地图 Web 服务；返回结构化地址 + 经纬度。


### 5.3.4 设备管理

#### 5.3.4.1 设备绑定

**功能说明**：让用户预先登记常用设备，形成"我的设备库"，作为下单、诊断、售后的快捷来源。

**实现流程**：① device-edit 页面通过设备类型、品牌、型号逐级选择或拍照识别录入；② 补填序列号、成色、备注等；③ 数据写入 user_devices 表并与用户账号关联。

**技术要点**：设备类型/品牌/型号来自统一字典表，保证数据一致性；同类型设备可多条存在，便于多设备管理。

**数据与接口**：涉及 user_devices 表；设备 CRUD 接口。

#### 5.3.4.2 设备档案维护

**功能说明**：集中展示与管理用户所有设备，区分维修/回收用途，方便快速发起业务。

**实现流程**：① my-devices 页面按用途区分展示设备列表；② 支持编辑、删除与设为默认设备；③ 单用户设备数量设上限（10 台），超出时提示精简。

**技术要点**：默认设备在下单时优先带入；删除需确认以免误操作。

**数据与接口**：涉及 user_devices 表；设备列表/编辑/删除接口。

#### 5.3.4.3 拍照识别型号

**功能说明**：通过拍照/相册识图自动识别设备型号，减少手动录入，提升录入准确率与效率。

**实现流程**：① scan 页面调用 `wx.chooseImage` 拍照或选图；② 上传至 `POST /api/scan/identify`；③ 后端基于 AI 视觉识别返回型号候选列表；④ 用户确认后自动写入设备库或预填下单表单。

**技术要点**：识别结果提供候选与置信度，用户可纠正；识别失败时允许回退手动输入。

**数据与接口**：涉及 `POST /api/scan/identify`、`wx.chooseImage`；返回识别型号候选。

#### 5.3.4.4 设备售后总览

**功能说明**：让用户在一个页面看清设备的质保、维修履历与保养建议，掌握设备全生命周期健康状况。

**实现流程**：① 进入 device-detail 调用 afterSalesApi；② 聚合展示质保状态、历史维修记录、保养建议；③ 以模块卡片分区呈现，并提供跳转入口。

**技术要点**：数据来自多张业务表聚合，接口层做合并返回，减少前端多次请求。

**数据与接口**：涉及 afterSalesApi；聚合 user_devices、order、after_sales 等数据。

#### 5.3.4.5 质保维修入口

**功能说明**：对质保期内设备提供专属维修入口，关联原订单发起时可免检测费，提升售后体验。

**实现流程**：① 在设备详情/售后页判断设备是否在质保期；② 质保期内展示"质保维修"入口；③ 点击后携带设备与原订单上下文进入维修下单，走免检测费（applyWarranty）逻辑。

**技术要点**：质保期由订单内的质保起始日期与服务时长计算；免检资格由服务端校验、不被前端绕过。

**数据与接口**：涉及 applyWarranty；关联 order、user_devices。

### 5.3.5 AI 故障自检

#### 5.3.5.1 四步诊断向导

**功能说明**：以向导式提问引导用户结构化描述故障，为 AI 分析提供规范输入，降低描述难度。

**实现流程**：① diagnose 页面采用四步向导：选择设备类型（10 类）→ 选择品牌 → 选择故障现象 → 补充故障详情；② 每一步通过后才进入下一步，进度提示清晰；③ 完成四步后汇总形成诊断请求。

**技术要点**：设备类型/品牌/现象均来自字典，保证枚举可控；自定义项作为兜底。

**数据与接口**：涉及诊断数据字典与 `POST /api/diagnose/analyze` 上游输入。

#### 5.3.5.2 品牌/故障自定义输入

**功能说明**：允许用户补充字典外品牌与非常见故障，覆盖冷门设备，避免因枚举不全而无法诊断。

**实现流程**：① 在品牌与故障现象步骤提供"自定义输入"；② 用户输入内容经去空格、长度校验后并入请求参数；③ 作为补充描述随诊断请求提交。

**技术要点**：自定义内容不进主导航的字典，仅作用于本次诊断，避免污染公共枚举。

**数据与接口**：涉及诊断请求参数；与字典项合并后传后端。

#### 5.3.5.3 大模型故障分析

**功能说明**：借助大模型对故障进行智能归因，输出诊断结论、可能原因、维修建议与预估费用，实现 AI 自助预诊。

**实现流程**：① 前端提交诊断信息至 `POST /api/diagnose/analyze`；② 后端构造结构化提示词，调用 DeepSeek 大模型；③ 解析返回的诊断结论、可能原因（含概率）、维修建议、预估费用区间；④ 以卡片形式分块呈现给用户。

**技术要点**：提示词工程保证输出结构化 JSON；对模型输出做安全与格式兜底解析，失败时降级给出通用建议。

**数据与接口**：涉及 `POST /api/diagnose/analyze`；依赖 DeepSeek 模型服务。

#### 5.3.5.4 诊断结果转下单/转客服

**功能说明**：打通"诊断—下单—咨询"链路，让诊断结果直接转化为业务动作。

**实现流程**：① 诊断结果页提供"立即维修下单"与"咨询客服"两个动作；② 转下单时预填已选设备与故障信息；③ 转客服时将诊断上下文带入智能客服会话，便于后续追问。

**技术要点**：上下文以结构化参数携带，减少二次录入；动作跳转保持参数链路完整。

**数据与接口**：涉及下单上下文体与智能客服入参。

### 5.3.6 智能客服

#### 5.3.6.1 多智能体意图路由

**功能说明**：将用户各种提问自动分发到最合适的专业智能体处理，提升回答精准度与专业性。

**实现流程**：① 用户消息发送至 `POST /api/chat/message`；② 后端 routerAgent 对消息做意图识别；③ 按意图将请求分发至 faqAgent（知识库问答）、queryAgent（订单/报价查询）、repairRecycleAgent（维修/回收咨询）等专业智能体之一。

**技术要点**：路由规则基于关键词 + 语义推理结合；抽象出统一消息封装，各智能体输出统一反馈给用户。

**数据与接口**：涉及 `POST /api/chat/message`、routerAgent 各子智能体。

#### 5.3.6.2 知识库问答

**功能说明**：基于系统知识库回答常见问题与维修知识，实现 7×24 自助答疑。

**实现流程**：① faqAgent 收到路由过来的知识类问题；② 调用 `POST /api/knowledge/retrieve` 进行 RAG 检索；③ 召回相关条目并结合大模型生成回答；④ 回答经排版后返回用户。

**技术要点**：检索采用向量 + 关键词混合召回；回答附引用来源增强可信度。

**数据与接口**：涉及 `POST /api/knowledge/retrieve`、knowledge_base 知识库。

#### 5.3.6.3 快捷短语与建议动作

**功能说明**：通过预设快捷短语与可点击的动作按钮，降低用户输入成本，快速触达高频服务。

**实现流程**：① 客服界面提供快捷短语区（如"营业时间""维修流程""回收怎么算"）；② 点击短语直接作为用户消息发送；③ 部分场景提供建议动作按钮（跳转下单、查看订单等）。

**技术要点**：快捷内容可配置化管理（配合管理端维护），动作按钮携带路由参数直达业务页。

**数据与接口**：涉及客服前端交互与快捷内容配置。

#### 5.3.6.4 语音转文字

**功能说明**：支持语音消息实时转文字，方便不便打字的场景，提升沟通效率。

**实现流程**：① 用户按住录音按钮采集音频（需 `scope.record` 麦克风授权）；② 音频上传至 `POST /api/chat/transcribe`；③ 经阿里云 DashScope ASR 转写为文字；④ 文字进入消息流，作为普通消息处理。

**技术要点**：录音时长与大小做限制；转写失败时提示用户改用文字输入；授权被拒时给出引导。

**数据与接口**：涉及 `POST /api/chat/transcribe`、阿里云 DashScope ASR、`scope.record`。

#### 5.3.6.5 转人工客服

**功能说明**：在智能体无法满足需求时平滑转接人工，保证服务质量不降级。

**实现流程**：① 用户可发起转人工（`POST /api/chat/transfer-to-human`）；② 前端轮询 `GET /api/chat/human-status` 获取人工在线状态；③ 管理端有客服在线并认领后，会话进入人工通道，智能体与人工可在会话中切换。

**技术要点**：转接需携带上下文避免重复说明；无人值守时给出"稍后再试/留言"提示。

**数据与接口**：涉及 `POST /api/chat/transfer-to-human`、`GET /api/chat/human-status`、WebSocket 通道。

#### 5.3.6.6 预约维修

**功能说明**：客服会话内直接发起维修预约，实现"咨询即预约"的转化闭环。

**实现流程**：① 会话中提供"预约维修"按钮；② 用户点击后弹出预约表单（设备、时间、地址）；③ 预约信息带入下单流程并创建预约记录；④ 后续由管理员跟进确认。

**技术要点**：预约与下单解耦，先占位后续完善；时间冲突做前端可选性校验。

**数据与接口**：涉及预约创建接口与下单上下文。

#### 5.3.6.7 会话历史管理

**功能说明**：持久化保存用户与客服的历史会话，支持按需回看、继续与清理。

**实现流程**：① 会话、消息经 chatPersistenceRoutes 写入 chat_conversations 与 chat_messages 表；② 前端提供会话列表、按日期分组、继续会话、删除会话与清空历史；③ 重新进入自动加载最近会话。

**技术要点**：消息按时间顺序落库，事务保证一致性；历史会话数据用于客服复盘与质检。

**数据与接口**：涉及 chat_conversations、chat_messages 表及相应接口。

#### 5.3.6.8 上下文带入下单

**功能说明**：将客服或诊断环节沉淀的设备、故障信息带入维修下单，避免重复填写，缩短服务路径。

**实现流程**：① 客服/诊断结果构建业务上下文对象；② 用户点击"去下单"携带上下文；③ 下单表单自动预填设备、品牌、故障描述；④ 用户仅需确认或微调后提交。

**技术要点**：上下文交接采用清晰的参数契约；预填字段允许用户覆盖。

**数据与接口**：涉及下单上下文传递、下单表单预填。

### 5.3.7 维修下单

#### 5.3.7.1 多步骤下单表单

**功能说明**：将复杂的维修下单拆分为多步引导，降低填写负担，保证信息完整。

**实现流程**：① repair 页面以步骤条分步引导"设备→品牌型号→故障→服务安排→确认"；② 每一步校验通过后才解锁下一步；③ 最后在确认页汇总全部信息后提交。

**技术要点**：表单状态集中管理；分步校验减少后端无效请求；返回上一步保留已填数据。

**数据与接口**：涉及下单表单状态机与创建订单接口。

#### 5.3.7.2 设备/品牌/型号选择

**功能说明**：通过级联选择快速锁定目标设备，保证订单设备信息规范统一。

**实现流程**：① 设备类型、品牌、型号均来自 device_types、brands 字典表；② 前端实现三级级联选择，数据实时联动过滤；③ 字典外设备支持自定义补充。

**技术要点**：级联数据按需加载减少请求量；自定义补充仅在本次有效。

**数据与接口**：涉及 device_types、brands 表及级联字典接口。

#### 5.3.7.3 故障现象选择与补充描述

**功能说明**：帮助维修人员提前了解故障特征，提升报价与维修的针对性。

**实现流程**：① 提供常用故障现象选项（如不开机、黑屏、续航差等）；② 支持补充文字描述；③ 故障信息随订单提交并供维修端展示。

**技术要点**：故障现象归一化到枚举便于统计；补充描述支持富文本。

**数据与接口**：涉及订单故障字段；供维修端订单详情读取。

#### 5.3.7.4 图片上传

**功能说明**：上传设备照片或故障图片，便于维修人员远程初判，减少送修沟通成本。

**实现流程**：① 选择或拍摄图片；② 图片经 multer 接收、sharp 压缩后持久化到 uploads 目录；③ 返回 URL 与订单关联，支持多图上传与预览。

**技术要点**：图片压缩限尺寸限体积；对 MIME 做校验防恶意文件。

**数据与接口**：涉及图片上传接口与订单图片关联字段。

#### 5.3.7.5 服务方式选择

**功能说明**：支持"到店"与"上门"两种服务模式，满足不同客户场景。

**实现流程**：① 用户在服务安排步选择"到店/上门"；② 上门时展开地址与单位选择，并可能关联配送；③ 到店则提示门店/服务点信息。

**技术要点**：服务方式影响订单后续流转（上门需配送分配）；不同方式展示不同的地址填写逻辑。

**数据与接口**：涉及订单 service_mode 字段与地址/单位关联。

#### 5.3.7.6 地址与单位关联

**功能说明**：将上门订单与已保存的收货地址或企业单位关联，自动带入联系人信息。

**实现流程**：① 上门订单可下拉选择已保存地址或单位；② 选中后自动填入联系人、电话、详细地址；③ 未保存时允许临时新增。

**技术要点**：地址/单位复用个人中心数据源，保证一致性；临时新增遵循相同校验规则。

**数据与接口**：涉及 user_addresses / user_units 与订单地址快照。

#### 5.3.7.7 估价展示

**功能说明**：提交前展示预估维修价格，体现"透明定价"的服务理念，管理用户费用预期。

**实现流程**：① 根据所选设备类型/故障，读取价格表费率；② 计算"基础价 × 费率"得到预估区间；③ 在确认页展示给用户；④ 最终报价以管理员核定为准。

**技术要点**：估价与正式报价分离，明确告知为预估；实时计算避免写死。

**数据与接口**：涉及 prices 价格表、估价计算逻辑。

### 5.3.8 回收流程与估价

#### 5.3.8.1 回收品类浏览

**功能说明**：向用户展示可回收设备品类，引导进入回收估价流程。

**实现流程**：① recycle 页面提供 12 类回收品类（手机、电脑、平板、穿戴、显示器、数码、相机、游戏、无人机、服务器、网络设备、显卡）浏览入口；② 品类数据来自 recycleData.js 配置；③ 点击进入对应品牌/型号选择。

**技术要点**：品类以图标 + 名称卡片呈现，提升视觉引导。

**数据与接口**：涉及 recycleData.js 品类配置。

#### 5.3.8.2 品牌型号选择与搜索

**功能说明**：快速定位目标回收设备，提供按品牌型号逐级选择与全局模糊搜索。

**实现流程**：① 支持按品牌、型号逐级筛选；② 顶部提供全局模糊搜索（含本地存储的搜索历史）；③ 命中后进入设备报价/状态问答。

**技术要点**：搜索历史本地持久化提升体验；搜索与筛选结果实时联动。

#### 5.3.8.3 回收估价问答

**功能说明**：以问答式选配收集设备状态（成色、配置、维修史等），为估价提供参数。

**技术要点**：问答项动态化配置，适配不同品类；选配不可跳跃以保证估价准确。

**数据与接口**：涉及估价问答配置与估价输入参数。

#### 5.3.8.4 本地估价计算与价格区间

**功能说明**：基于选配参数在本地即时计算回收估价，让用户第一时间了解设备回收价值。

**实现流程**：① 收集用户选配的成色、配置、维修史等参数；② 前端通过 calculateLocalEstimate 按品类价格表本地计算；③ 输出区间估价（如中高价/中低价/最高价）并展示；④ 用户可调整选配实时刷新估价。

**技术要点**：本地计算减少服务端请求延迟；估价仅作参考，最终以平台人员核价为准。

**数据与接口**：涉及 calculateLocalEstimate 逻辑与回收价格配置；输出价格区间。

#### 5.3.8.5 回收下单

**功能说明**：确认估价后提交回收订单，正式发起回收流程。

**实现流程**：① 用户确认估价与所选设备状态；② 选择发件地址并上传设备图片；③ 调用 createRecycleOrder 生成回收订单；④ 订单进入独立回收流程，由平台后续跟进确认与付款。

**技术要点**：回收订单与维修订单流程解耦；地址/图片复用既有上传链路。

**数据与接口**：涉及 createRecycleOrder 与回收订单表。


### 5.3.9 报价与确认

#### 5.3.9.1 管理员提交报价

**功能说明**：维修管理员在检测后为订单核定维修费用并录入报价明细，实现费用的正式确认。

**实现流程**：① 管理员对待处理订单录入报价金额、说明与检测报告文件；② 提交后订单进入 quoted（待确认报价）状态；③ 报价过程与修改均留存操作记录，可追溯。

**技术要点**：报价与初期估价分离，报价以检测结果为依据；报价状态驱动订单流转。

**数据与接口**：涉及报价接口与订单 quoted 状态、报价明细表。

#### 5.3.9.2 用户查看报价明细

**功能说明**：让用户在决定前清晰了解维修费用构成，保障消费知情权。

**实现流程**：① 用户在订单详情页查看报价金额、维修说明与附件报告；② 报价明细逐项展示（人工、配件、检测费等）；③ 明细清晰可查，便于用户权衡。

**技术要点**：报价明细结构化返回，前端分项展示；附件支持在线预览。

**数据与接口**：涉及订单详情接口与报价明细数据。

#### 5.3.9.3 用户接受报价

**功能说明**：用户确认报价后进入支付环节，正式启动维修。

**实现流程**：① 用户在订单详情点击"接受报价"；② 调用 `PUT /api/orders/:orderId/accept-quote`；③ 订单流转至 confirmed 状态；④ 前端引导进入支付流程。

**技术要点**：接受报价操作需用户明确确认；状态流转由服务端强制校验，防止越权。

**数据与接口**：涉及 `PUT /api/orders/:orderId/accept-quote` 与订单 confirmed 状态。

#### 5.3.9.4 用户拒绝报价

**功能说明**：允许用户对不满意的报价拒绝并说明原因，返回重新协商，保障公平。

**实现流程**：① 用户点击"拒绝报价"并填写拒绝原因；② 调用 reject-quote 接口；③ 订单回到 pending 状态由管理员重新报价；④ 拒绝记录持久化，全程可追溯。

**技术要点**：拒绝原因必填并结构化存储；防止无限循环，可设置重新报价次数/时限提示。

**数据与接口**：涉及 reject-quote 接口、订单 pending 状态与拒绝记录。

#### 5.3.10.1 进度百分比上报

#### 5.3.10.4 进度时间线展示

**实现流程**：① progress-feedback 页面读取订单全部进度节点；② 按时间正序以时间线样式渲染；③ 文字、图片、视频分区展示，可点击查看大图/播放。

**技术要点**：时间线按创建时间排序去重；节点状态区分（待审核/已确认）增强信息维度。

### 5.3.12 微信支付

#### 5.3.12.1 创建支付单

**功能说明**：用户在确认报价后发起支付，通过微信支付安全完成线上结算。

**实现流程**：① 用户确认报价后调用 `POST /api/pay/create`；② wechatPayService 基于微信支付 API V3 完成 JSAPI 下单与 RSA-SHA256 签名；③ 返回前端调用支付所需的参数（发起支付所需参数）；④ 前端拉起微信支付收银台。

**技术要点**：商户密钥与证书安全存储；下单参数含金额、订单号、回调地址；金额以分存储避免浮点误差。

**数据与接口**：涉及 `POST /api/pay/create`、微信支付 V3 JSAPI 下单。

#### 5.3.12.2 支付结果查询

**功能说明**：主动核对支付状态，保证订单支付结果及时准确落库。

**实现流程**：① 提供 `GET /api/pay/query/:orderId`；② 前端在支付返回或轮询时调用；③ 后端（必要时调微信接口核验）返回支付状态；④ 成功则更新订单状态。

**技术要点**：查询与回调双通道保证一致性；以微信侧状态为准避免本地伪造。

**数据与接口**：涉及 `GET /api/pay/query/:orderId` 与订单支付状态。

#### 5.3.12.3 支付回调验签

**功能说明**：接收并验证微信异步通知，确保支付结果真实可信。

**实现流程**：① 微信以 POST 推送到 `POST /api/pay/notify`；② 后端验签（验证签名与证书）确认通知合法性；③ 验签通过后更新订单支付状态并返回成功应答；④ 验签失败返回失败并记录异常。

**技术要点**：返回报文需符合微信格式以防重发；幂等处理避免重复更新。

**数据与接口**：涉及 `POST /api/pay/notify`、微信支付回调验签。

#### 5.3.12.4 退款申请与退款回调

**功能说明**：支持订单退款（含取消/售后场景），完成资金的逆向流转。

**实现流程**：① 符合条件的订单由管理员发起退款（`POST /api/pay/refund/apply`）；② 走微信支付退款通道；③ 监听退款异步通知同步退款状态；④ 退款结果更新订单与售后记录。

**技术要点**：退款金额不超已付金额；退款状态机（处理中/成功/失败）完整记录。

**数据与接口**：涉及 `POST /api/pay/refund/apply`、退款回调接口。

#### 5.3.12.5 内部人员免付款订单

**功能说明**：满足内部送修、测试等场景，内部人员下单可免在线支付。

**实现流程**：① internal 角色下单时可标记为免付款（waived）；② 提交后经管理员确认；③ 确认后订单跳过支付环节直接进入维修；④ 内部订单状态与费用清晰区分。

**技术要点**：免付款资格由角色在服务端校验，防止普通用户滥用；费用记为内部结算。

**数据与接口**：涉及订单 waived 标记与下单接口。

### 5.3.13 订单评价

## 5.4 管理端功能模块

管理端功能模块内嵌于小程序，面向维修管理员与超级管理员，提供订单处理、用户/设备/价格管理、进度审批、配送分配、数据统计与人工客服等运营管理能力。该端与客户端共用同一套 Node.js 后端接口，通过登录身份中的角色标识进入管理工作台，实现"一部手机管门店"的轻量运营形态。

### 5.4.1 管理员登录与工作台

#### 5.4.1.1 管理员手机号登录

**功能说明**：提供区别于顾客微信登录的管理员身份认证入口，保障后台操作主体明确。

**实现流程**：① 管理员通过 admin-login 页面以手机号 + 密码（或验证码）登录；② 调用 `POST /api/admin/login`；③ 后端校验账号、角色与状态；④ 登录成功后签发令牌并进入管理后台。

**技术要点**：账号需绑定 admin/super_admin 角色方可进入；登录失败次数限制防爆破。

**数据与接口**：涉及 `POST /api/admin/login`、管理账号表。

#### 5.4.1.2 工作台与待办角标

**功能说明**：以工作台聚合待处理事项，帮助管理员快速定位优先任务。

**实现流程**：① admin 首页为工作台；② 请求 `GET /api/admin/pending-count` 获取待处理工单与待确认报价等计数；③ 以角标/卡片形式展示待办；④ 点击直达对应列表。

**技术要点**：待办计数按角色实时聚合；工作台与各列表状态数据联动。

**数据与接口**：涉及 `GET /api/admin/pending-count` 与订单/报价待办统计。

#### 5.4.1.3 管理入口角色控制

**功能说明**：仅向管理员角色开放管理入口，防止普通用户误入后台。

**实现流程**：① 前端根据用户角色标识控制管理入口显示；② 仅 admin/super_admin 可见管理入口；③ 服务端接口再次以中间件校验角色，双重防护。

**技术要点**：前端控制 + 接口强制双层防线，杜绝仅前端隐藏导致的越权。

**数据与接口**：涉及角色标识渲染逻辑与 adminAuth 中间件。

### 5.4.2 订单/工单管理

#### 5.4.2.1 订单列表与状态筛选

**功能说明**：集中管理全部订单，按状态快速检索待办与历史订单。

**实现流程**：① admin-orders 页面加载订单列表；② 支持按状态筛选（待处理/待确认报价/维修中/已完成等）；③ 支持按订单号/客户/设备关键字检索。

**技术要点**：列表分页 + 懒加载保证性能；筛选条件组合查询。

**数据与接口**：涉及订单列表接口与订单状态字段。

#### 5.4.2.2 订单详情查看

**功能说明**：让管理员在一个页面掌握订单全量信息，为接单报价提供依据。

**实现流程**：① 管理员打开订单详情；② 查看设备、故障、地址、报价、进度、支付等全量信息；③ 各区块结构化展示，支持快捷操作入口。

**技术要点**：详情接口聚合多表数据；操作按钮按状态动态可用。

**数据与接口**：涉及订单详情聚合接口。

#### 5.4.2.3 订单状态流转

**功能说明**：由管理员驱动订单主流程状态推进，保证业务流程受控。

## 5.5 Web 管理后台功能模块

Web 管理后台基于 PHP（ThinkPHP 8.1）构建，面向企业设备资产维护与维修运营场景，提供设备台账、工单全生命周期、维修人员排班、巡检保养、维修业务、支付进销存、统计报表、知识库与营销引流等完整管理能力，是系统的资产管理中枢。该端采用独立账号体系与独立 JWT，通过 roles / permissions / role_permissions 三表实现细粒度 RBAC 权限控制。

### 5.5.1 登录与 RBAC 权限管理

#### 5.5.1.1 账号密码登录

**功能说明**：提供后台账号密码认证，保障后台访问安全。

**实现流程**：① 后台采用账号密码登录（auth 路由）；② 密码经 bcrypt 加盐哈希存储，绝不存明文；③ 登录成功后签发 JWT 令牌；④ 后续请求携带令牌鉴权。

**技术要点**：密码哈希校验；登录失败限流；账号状态（禁用/启用）校验。

**数据与接口**：涉及 auth 路由、后台用户表。

#### 5.5.1.2 access/refresh 双令牌 JWT

**功能说明**：以双令牌机制在安全与体验间取得平衡。

**实现流程**：① 采用 access token + refresh token 双令牌；② access token 短期有效用于接口鉴权；③ refresh token 用于过期后自动续期；④ 刷新时校验 refresh token 有效性并重签 access token。

**技术要点**：refresh token 可作废/轮换防重放；两令牌签名与有效期策略分开。

**数据与接口**：涉及令牌签发/刷新路由。

#### 5.5.1.3 用户管理

**功能说明**：统一管理后台操作人员账号。

**实现流程**：① 提供后台用户的新增、编辑、禁用与删除；② 维护账号角色归属；③ 禁用后无法登录；④ 记录账号操作日志。

**技术要点**：账号解绑/停用即时生效；超级管理员不可被轻易删除。

**数据与接口**：涉及后台用户 CRUD 接口与账号表。

#### 5.5.1.4 角色/权限管理

**功能说明**：实现细粒度的 RBAC 权限分配，控制不同后台角色的菜单与接口访问。

**实现流程**：① 通过 roles、permissions、role_permissions 三表实现 RBAC；② 可自定义角色并分配菜单/接口权限；③ 权限校验由 PermissionCheck 中间件强制执行；④ 权限变更即时影响访问。

**技术要点**：权限按"菜单 + 接口"双重分配；中间件逐请求校验。

**数据与接口**：涉及 roles / permissions / role_permissions 表及权限管理接口。

**实现流程**：① mini-admin 采用独立账号体系与独立 JWT；② 与主后台权限隔离；③ 专供小程序运营人员管理。

**技术要点**：独立令牌、独立角色，避免权限混用。

**数据与接口**：涉及 mini-admin 独立认证体系。

#### 5.5.14.2 订单管理

**功能说明**：运营人员管理小程序侧订单。

**实现流程**：① 管理小程序侧订单；② 支持订单查询、状态处理；③ 与 Node 端订单数据同步（miniprogram_order_mapping）。

**技术要点**：跨端订单数据映射同步，保证一致性。

**数据与接口**：涉及 miniprogram_order_mapping 及订单管理接口。

#### 5.5.14.3 进度/进度申请管理

**功能说明**：管理小程序侧维修进度与进度申请。

**实现流程**：① 管理维修进度与进度申请；② 审批用户提交的进度申请；③ 与小程序端进度数据双向同步（miniprogram_progress_sync）。

**技术要点**：跨端进度同步；审批结果回写小程序端。

**数据与接口**：涉及 miniprogram_progress_sync 及进度管理接口。

#### 5.5.14.4 用户/地址/品牌/设备类型管理

**功能说明**：维护小程序基础运营数据，保证运营管理一致性。

**实现流程**：① 管理小程序用户、地址、品牌与设备类型等基础数据；② 支持增删改查；③ 与小程序端运营数据保持一致。

**技术要点**：基础数据跨端同步；字典数据统一。

**数据与接口**：涉及基础数据管理接口与跨端同步。

## 5.6 智能客服 Agent 功能模块

智能客服 Agent 基于 Python（FastAPI + LangGraph）构建，作为系统的智能大脑，通过多智能体工作流与 RAG 知识库检索，为客服问答与业务咨询提供智能化能力支撑。Agent 可同时访问 repair 与 cmms_db 数据库，实现跨库业务数据联动。

### 5.6.1 智能体工作流

#### 5.6.1.1 LangGraph 状态机

**功能说明**：以状态机编排多智能体对话流程，实现可控的智能对话。

**实现流程**：① 采用 LangGraph 构建智能体状态机；② 按"初始化状态→加载用户状态→分析→回答"节点链路组织推理；③ 每节点处理特定职责；④ 实现可控对话编排。

**技术要点**：状态节点可复用、可扩展；流程可视化便于调试。

**数据与接口**：涉及 LangGraph 工作流定义。

#### 5.6.1.2 用户状态加载

**功能说明**：加载用户相关业务状态，为个性化回答提供上下文。

**实现流程**：① 从 repair 与 cmms_db 双库加载用户历史订单、设备等状态；② 构造问答上下文；③ 供后续回答引用。

**技术要点**：跨库聚合用户画像；上下文时效性管理。

**数据与接口**：涉及双库数据访问。

#### 5.6.1.3 场景识别

**功能说明**：识别用户输入所属业务场景，决定后续对话路由。

**实现流程**：① 分析用户输入意图；② 识别所属业务场景（维修下单、库存、人员、知识库、概览、通用）；③ 输出场景标签供路由。

**技术要点**：场景识别结合关键词 + 语义；支持多场景意图。

**数据与接口**：涉及场景识别模型与分类逻辑。

#### 5.6.1.4 场景路由

**功能说明**：按识别结果将请求路由至对应场景节点处理。

**实现流程**：① 根据场景标签将请求路由至对应节点；② 节点调用相应数据访问逻辑；③ 实现领域化处理。

**技术要点**：路由规则与场景映射可配置；未知场景走通用兜底。

**数据与接口**：涉及场景路由与请求分发。

#### 5.6.1.5 回答生成

**功能说明**：结合场景数据与大模型生成自然语言回答。

**实现流程**：① 结合场景数据与大模型（DeepSeek）生成回答；② 组织提示词与检索上下文；③ 返回自然语言回答给客服前端。

**技术要点**：大模型输出安全与合规校验；生成失败降级。

**数据与接口**：涉及大模型调用与回答返回。

### 5.6.2 RAG 知识库检索

#### 5.6.2.1 知识向量化

**功能说明**：构建可语义检索的知识索引，支撑 RAG。

**实现流程**：① 将知识库内容分块（kb_chunks）；② 向量化存储；③ 构建语义检索索引。

**技术要点**：分块策略影响检索精度；向量库选择（Milvus）。

**数据与接口**：涉及 kb_chunks 与向量化/存储流程。

#### 5.6.2.2 检索增强生成

**功能说明**：通过 RAG 提升回答准确性与专业性。

**实现流程**：① 基于 DeepSeek 大模型与检索上下文实现检索增强生成（RAG）；② 先检索后生成；③ 回答附知识来源。

**技术要点**：检索结果排序与截断；上下文窗口管理。

**数据与接口**：涉及 RAG 生成流程与大模型调用。

#### 5.6.2.3 双库数据访问

**功能说明**：为智能体提供跨库数据支撑，实现业务数据联动。

**实现流程**：① data_access 模块统一访问 repair 与 cmms_db 双库；② 按业务封装数据读取；③ 供智能体各节点调用。

**技术要点**：双库连接与事务管理；数据抽象层复用。

**数据与接口**：涉及 data_access 模块与双库数据源。
