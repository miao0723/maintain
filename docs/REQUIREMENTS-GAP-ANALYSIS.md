# 需求差异分析报告

**文档生成时间**: 2026-03-23
**对比依据**: 《维修全流程管理.pdf》电脑端需求 vs 当前CMMS系统实现

---

## 执行摘要

### 总体对比结果

| 维度 | PDF需求模块数 | 已实现模块数 | 实现率 | 状态 |
|------|--------------|------------|--------|------|
| **功能模块** | 7大模块 | 13个阶段 | - | ⚠️ 部分匹配 |
| **子功能项** | 33个子功能 | 40+个功能 | - | ⚠️ 功能偏移 |
| **核心业务** | 维修业务为主 | 设备维护为主 | - | ❌ 业务方向差异 |

### 关键发现

1. **❌ 业务方向不一致**: PDF聚焦"维修公司业务系统"，当前系统是"企业设备维护管理(CMMS)"
2. **⚠️ 功能重叠度低**: 仅6个功能有交集 (支付/发票/引流/客服/合同/参数)
3. **✅ CMMS功能完整**: 当前系统作为设备维护系统功能完整，只是不匹配PDF的维修公司需求
4. **⚠️ 需求理解偏差**: 两个系统解决不同场景的维护管理问题

## 系统定位差异分析

### PDF系统定位：维修公司业务管理系统

**目标用户**: 维修服务提供商
**业务模式**: B2C - 接收客户维修请求，提供有偿维修服务
**核心流程**: 获客 → 报价 → 合同 → 维修 → 交付 → 收款
**关键特征**:
- 面向外部客户(用户、单位)
- 包含营销引流(抖音、客服)
- 包含商业流程(合同、支付、发票)
- 维修多种机械(非自有的客户机械)

### 当前系统定位：企业设备维护管理系统(CMMS)

**目标用户**: 设备拥有企业(工厂、医院、学校等)
**业务模式**: 内部服务 - 管理自有设备的维护保养
**核心流程**: 故障上报 → 派单 → 维修 → 验收 → 分析
**关键特征**:
- 面向内部用户(员工、部门)
- 包含计划性维护(巡检、保养)
- 包含成本核算(非实际支付)
- 管理自有设备资产

## 建议方案

### 方案A：转向PDF需求(重大重构)

**工作量**: 需重构60%以上代码
**工期**: 3-4个月

**需要新增**:
1. 客户管理模块(Customer)
2. 合同管理模块(Contract)
3. 支付对接(PaymentGateway + 微信/支付宝SDK)
4. 发票管理(Invoice)
5. 报告模板系统(ReportTemplate + 检测/测试/维修报告)
6. 营销引流模块(Marketing + 抖音API)
7. 客服系统(CustomerService + 第三方SDK)
8. SLA超时监控
9. 操作日志审计
10. RBAC权限系统

**需要改造**:
1. Device → 改为CustomerMachine(客户机械)
2. WorkOrder → 改为RepairOrder(维修订单)
3. 去除巡检、保养、排班等内部维护功能
4. 增加报价、合同、支付流程

**风险评估**:
- ❌ 破坏现有CMMS功能完整性
- ❌ 3-4个月开发周期
- ❌ 需求理解可能仍有偏差
- ⚠️ PDF可能不是唯一需求来源

### 方案B：保持CMMS定位，增强核心功能(推荐)

**工作量**: 中等
**工期**: 1个月

**保持**:
- 现有设备维护管理定位
- 工单流转、巡检、保养等核心功能

**增强**:
1. **完善JWT认证** - 修复AuthController，使用标准JWT
2. **操作日志** - 新增操作审计功能
3. **系统参数** - 新增配置管理
4. **权限细化** - 增强RBAC权限控制
5. **报表增强** - 支持PDF/Excel导出
6. **移动端优化** - 完善微信小程序功能

**优势**:
- ✅ 保持系统完整性
- ✅ 工期可控
- ✅ 功能更聚焦
- ✅ 符合CMMS行业标准

### 方案C：双模式运行(灵活架构)

**工作量**: 大
**工期**: 2-3个月

**设计思路**:
- 核心系统保持CMMS功能
- 通过"业务模式切换"支持两种场景:
  - 模式1: 内部设备维护(当前实现)
  - 模式2: 对维修服务(扩展实现)

**技术方案**:
```php
// 系统配置表新增模式字段
system_configs.mode = 'internal' | 'service'

// 根据模式显示不同功能
if (config('mode') === 'service') {
    // 显示: 客户管理、合同、支付、发票等
    // 隐藏: 巡检、保养、排班等内部功能
} else {
    // 显示: 巡检、保养、排班等
    // 隐藏: 客户、合同、支付等
}
```

**优势**:
- ✅ 支持两种业务场景
- ✅ 代码复用度高
- ✅ 灵活切换

**劣势**:
- ⚠️ 架构复杂度增加
- ⚠️ 维护成本增加
